---
title: ContextMenu
description: A menu for a control, at the pointer or from the keyboard.
---

`ContextMenu` gives a control a menu. The menu opens on the platform's secondary press (a right-click, or a Control-click on a Mac) or a long touch, at the pointer. From the keyboard, `Shift+F10` or the context menu key opens it beside the focused control, and a screen reader's "show menu" action does the same. Its items are the same [`Menu.Item`s](/docs/components/dropdown-menu#items) as a DropdownMenu's.

<Demo name="context-menu" height={300} />

```tsx
import { ContextMenu, Knob, Menu } from '@soundor/components';
import { parameters } from 'soundor:parameters';

<ContextMenu>
  <ContextMenu.Trigger>
    <Knob parameter={parameters.gain} />
  </ContextMenu.Trigger>
  <ContextMenu.Content>
    <Menu.Item onPress={reset}>Reset</Menu.Item>
    <Menu.Divider />
    <Menu.Item onPress={copy}>Copy value</Menu.Item>
    <Menu.Item onPress={paste} disabled={!canPaste}>
      Paste value
    </Menu.Item>
  </ContextMenu.Content>
</ContextMenu>;
```

The content renders as the menu opens, so the items show the state at that moment: `disabled={!canPaste}` is read then. A menu whose content renders no item at all closes as it opens.

## With parameter controls

`ParameterMenuItems` renders a parameter's usual items:

- **Reset to default**: one host gesture and one undo step, as a double-click is. It is disabled when the parameter is already at its default.
- **Enter value…**: only with `onEnterValue`. It calls your function to open a field of your own, as the demo's `Modal` does.
- **Copy value** and **Paste value**: the parameter's own `format()` goes to the system clipboard, and pasted text is read back with its `parse()`. Text that isn't a value changes nothing. `clipboard={false}` leaves them out.

```tsx
import {
  ContextMenu,
  Knob,
  Menu,
  ParameterMenuItems,
} from '@soundor/components';

<ContextMenu>
  <ContextMenu.Trigger>
    <Knob parameter={parameters.gain} />
  </ContextMenu.Trigger>
  <ContextMenu.Content>
    <ParameterMenuItems parameter={parameters.gain} />
    <Menu.Divider />
    <Menu.Item onPress={learn}>MIDI learn</Menu.Item>
  </ContextMenu.Content>
</ContextMenu>;
```

Put items of your own before or after them. A read-only parameter's items are disabled, except Copy. `labels` gives them in your language.

Parameter context menus aren't added to the controls automatically: give the ones that should have one a ContextMenu. A component of yours keeps that short:

```tsx
function WithMenu({
  parameter,
  children,
}: {
  parameter: RangeParameter;
  children: ReactElement<HostProps>;
}) {
  return (
    <ContextMenu>
      <ContextMenu.Trigger>{children}</ContextMenu.Trigger>
      <ContextMenu.Content>
        <ParameterMenuItems parameter={parameter} />
      </ContextMenu.Content>
    </ContextMenu>
  );
}
```

## The trigger keeps what it is

A context menu is a second way into a control, so `ContextMenu.Trigger` leaves the first one alone. It adds no view: its child lays out exactly as it would without it. The child keeps its role, its name, its value and state, its own actions, its focus, and its primary pointer and keys. A Knob stays a slider (`adjustable`), with the **show menu** action offered after its own increment, decrement, set value and reset.

Knob, Slider, Fader, XYPad and Plot markers act on the primary button only, so a secondary press starts no drag and opens no gesture. A secondary press during a primary drag opens nothing. Double-click reset and parameter bindings work as before. The menu's actions start host gestures only when they change a value.

The child is one element that takes a `ref` and `accessibilityActions`: any control of this library, or a `View`. Its own `ref`, actions and `onAccessibilityAction` keep working. A ContextMenu inside another's trigger takes the press, the keys and the action for its own control: the outer one opens only from the rest of its child.

For a group of controls, give the trigger a `View` around them. A secondary press, a long touch and the keys reach it from any control inside. A screen reader's action, though, is offered by the control it is on, and a plain `View` is not one: where each control should offer "show menu", give each its own ContextMenu.

```tsx
<ContextMenu>
  <ContextMenu.Trigger>
    <View style={{ flexDirection: 'row', gap: 12 }}>
      <Knob parameter={mix} />
      <Knob parameter={tone} />
    </View>
  </ContextMenu.Trigger>
  <ContextMenu.Content>
    <ParameterMenuItems parameter={mix} />
  </ContextMenu.Content>
</ContextMenu>
```

`disabled` on the ContextMenu opens no menu and offers no "show menu" action.

## Keyboard and accessibility

| Input                                | Does                                                          |
| ------------------------------------ | ------------------------------------------------------------- |
| Secondary press                      | Open at the pointer, with focus on the menu                   |
| A long touch                         | Open at the touch, with focus on the menu                     |
| `Shift+F10`, or the context menu key | Open beside the focused control, with focus on the first item |
| A screen reader's "show menu"        | Open beside the control, with focus on the first item         |
| `↑` / `↓`, `Home` / `End`, a letter  | Move between items                                            |
| `Enter`, `Space` or a click          | Run the item                                                  |
| `Esc`, `Tab` or a click outside      | Close, and give focus back to the control                     |

## Engine support

ContextMenu opens on Soundor's semantic `contextmenu` event, which the engine recognises on every view and dispatches as one cancellable event. What each platform sends is the engine's:

- **Secondary press:** the secondary button going down, or a Control-click on macOS, with its position in the view. The web runtime's own browser menu is kept away.
- **Clipboard:** `soundor:ui`'s `clipboard`. Copy and Paste are only offered where the runtime has one. A clipboard the platform refuses, such as a browser that denies permission to read it, makes them do nothing rather than fail.
- **Long touch:** the platform's long press, which is also the engine's `longpress` event. A touch that moves first, or is cancelled, is the control's drag.
- **"Show menu":** the engine's predefined `showContextMenu` accessibility action, added after the control's own. It is AXShowMenu on macOS, `ShowContextMenu` in UI Automation, `popup` in AT-SPI, and an action in VoiceOver's Actions rotor.
- **Context menu key:** `Shift+F10` and the context menu key, where the platform reports it.
- A menu is drawn inside the editor, as every Soundor overlay is, and is held within the editor's bounds. It can't extend past the plugin window as a system menu can.
